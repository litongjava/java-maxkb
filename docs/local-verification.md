# Java MossKB 本地验证记录

日期：2026-10-02。

## 已运行的服务

- 前端：`http://localhost:3000/ui/`，源代码位于相邻的 `MossKB/ui`。
- Java API：`http://localhost:10060`。
- 数据库：使用 `mosskb-web/my.txt` 中配置的 `moss_kb`。
- 推理：Gitee `deepseek-v4.1-flash`。
- 向量：Gitee `Qwen3-Embedding-8B`，1024 维。
- 扫描解析：Gitee `PaddleOCR-VL-1.5`。

密钥仅从本地忽略文件读取，模型种子 SQL 不包含密钥。

## 复现步骤

1. 在 `MossKB/ui` 安装前端依赖。
2. 在 Java 项目根目录执行 `scripts/Initialize-Database.ps1`，传入实际 PostgreSQL 的 `bin` 目录。
3. 执行 `scripts/Start-Local.ps1 -Build`。可通过参数指定 Java、Node 和 Maven 路径。重新构建前先停止旧 Java 进程。
4. 打开前端，进入“政法文档验证”知识库和“政法多轮问答验证”应用。

数据库初始化脚本已对当前数据库重复执行，已有表和测试数据保留。前端原有的四处合并冲突已解决并标记为已解决，没有创建合并提交。

## 文档解析异步化验证（2026-10-04）

分段预览原来在请求线程里同步等待整份解析，35 页扫描件要几分钟，而且远程 OCR 对空白页返回空正文时会直接抛 `OCR未返回正文`，让整份文档失败。本轮把它改成分段任务：上传立即返回任务 ID，解析在后台虚拟线程逐页推进，前端按 2 秒间隔轮询任务状态。

### 复现步骤

1. 在 `mosskb-web/my.txt` 加上 `http.multipart.max-request-size=110100480` 与 `http.multipart.max-file-size=104857600`。
2. 执行 `.\scripts\Initialize-Database.ps1`，新建 `moss_kb_document_split_task` 表。
3. 重新构建并启动后端，界面进入知识库创建流程选择文件。

### 验收记录

| 检查 | 结果 |
| --- | --- |
| 12,218,806 字节、35 页扫描件提交 | 1.5 秒返回任务 ID，请求线程不再等待 |
| 该文档解析结果 | `pdf-mixed`，28 页走 OCR、7 页走文本层，14 个分段，失败页 0 |
| 该文档第 35 页（空白页） | OCR 返回空正文，不再作废整份文档 |
| 227,449 字节、8 页文字件提交 | 0.1 秒返回任务 ID，`pdf-mixed`，1 页走 OCR，2 个分段 |
| 任务表进度 | `running` 期间按 5 页 / 5% 节流写库，完成后 `progress=100`、`total` 为实际页数 |
| 重复上传同一文件 | 页面缓存全部命中，不再产生 OCR 调用 |
| 单元测试 | `mvn test` 139 项通过（7 项跳过），其中新增空白页、重试、进度与任务状态用例 |
| 前端类型检查与构建 | `vue-tsc` 与 `vite build` 通过 |

上传体积上限必须写在本地配置文件里：打包在 jar 内的 `app.properties` 不会被当成有效配置，只有本地叠加的配置生效，未配置时上传会在解析请求头阶段直接断开连接。

界面行为与改造前一致，分段列表、解析策略与页数照常显示，区别是等待期间进度持续推进，且关掉页面后仍可重新取到同一个任务的结果。
